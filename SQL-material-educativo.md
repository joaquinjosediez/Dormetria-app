# `patient_education` — la tabla que nunca se creó

El panel **Material** del profesional está escrito desde hace tiempo y no
funciona: la tabla no existe. El comentario del código remitía a un "doc de
traspaso" que no está en el repo, y no había ningún SQL que la creara.

Se veía perfecto y no podía funcionar, porque la lectura usaba
`.catch(()=>[])`: sin tabla, el panel se dibujaba igual con todos los temas
en "Asignar".

```sql
-- ════════════════════════════════════════════════════════════════════
-- Dormetria · material educativo asignado por el profesional
-- Idempotente.
-- ════════════════════════════════════════════════════════════════════

create table if not exists public.patient_education (
  id            bigint generated by default as identity primary key,
  patient_email text        not null,
  doctor_email  text        not null,
  topic_id      text        not null,
  topic_title   text,
  assigned_at   timestamptz not null default now(),
  read_at       timestamptz
);

-- Un tema por paciente, una sola vez. Sin esto, tocar "Asignar" dos veces
-- deja dos filas y el paciente ve el mismo articulo repetido.
create unique index if not exists patient_education_unico
  on public.patient_education (lower(patient_email), topic_id);

create index if not exists patient_education_paciente_idx
  on public.patient_education (lower(patient_email), assigned_at desc);

alter table public.patient_education enable row level security;
```

## Las políticas

Cuatro, y cada una responde a una pregunta distinta.

```sql
-- 1 · El paciente LEE lo que le asignaron.
drop policy if exists pedu_paciente_lee on public.patient_education;
create policy pedu_paciente_lee
  on public.patient_education for select to authenticated
  using (
    lower(patient_email) in (
      select lower(email) from public.patients where auth_id = auth.uid()
    )
  );

-- 2 · Y marca que lo leyo. SOLO eso: el UPDATE no puede cambiar a quien
--     esta asignado ni quien lo asigno.
drop policy if exists pedu_paciente_marca_leido on public.patient_education;
create policy pedu_paciente_marca_leido
  on public.patient_education for update to authenticated
  using (
    lower(patient_email) in (
      select lower(email) from public.patients where auth_id = auth.uid()
    )
  )
  with check (
    lower(patient_email) in (
      select lower(email) from public.patients where auth_id = auth.uid()
    )
  );

-- 3 · El profesional ASIGNA, pero solo a SUS pacientes y solo en su
--     propio nombre. Las dos condiciones importan: sin la segunda,
--     cualquier profesional podria asignar firmando como otro.
drop policy if exists pedu_doctor_asigna on public.patient_education;
create policy pedu_doctor_asigna
  on public.patient_education for insert to authenticated
  with check (
    lower(doctor_email) = lower(auth.jwt() ->> 'email')
    and exists (
      select 1 from public.doctor_patients dp
      where lower(dp.doctor_email)  = lower(doctor_email)
        and lower(dp.patient_email) = lower(patient_email)
    )
  );

-- 4 · Lee y quita lo de sus pacientes.
drop policy if exists pedu_doctor_lee on public.patient_education;
create policy pedu_doctor_lee
  on public.patient_education for select to authenticated
  using (
    exists (
      select 1 from public.doctor_patients dp
      where lower(dp.doctor_email)  = lower(auth.jwt() ->> 'email')
        and lower(dp.patient_email) = lower(patient_email)
    )
  );

drop policy if exists pedu_doctor_quita on public.patient_education;
create policy pedu_doctor_quita
  on public.patient_education for delete to authenticated
  using (
    lower(doctor_email) = lower(auth.jwt() ->> 'email')
  );

notify pgrst, 'reload schema';
```

> **Sobre la policy 3.** Usa `auth.jwt() ->> 'email'`, no `auth.uid()`,
> porque es el criterio que ya usan las demás tablas del lado del
> profesional. Si en algún momento se unifica todo contra `doctors.auth_id`,
> esta hay que cambiarla junto con el resto — no antes, o queda inconsistente.

## Verificar

```sql
select policyname, cmd
from pg_policies
where schemaname='public' and tablename='patient_education'
order by cmd, policyname;
```

Tienen que salir cinco: un INSERT, un UPDATE, dos SELECT y un DELETE.

Y que efectivamente se pueda asignar:

```sql
select patient_email, topic_id, topic_title,
       assigned_at::date as asignado, read_at::date as leido
from public.patient_education
order by assigned_at desc
limit 20;
```

## Las policies que ya existían, y la que hay que borrar

Al correr el SQL de arriba la tabla quedó con **ocho** policies: las cuatro
de acá y otras cuatro que ya estaban de antes. Eso no es redundancia inocua.

> **Las policies PERMISSIVE se combinan con OR, no con AND.** Agregar una
> policy solo puede ampliar lo que se permite, nunca restringirlo. Una
> policy laxa anula a todas las estrictas que la acompañen.

Las ocho, con lo que hace cada una:

| policy | cmd | qué verifica |
|---|---|---|
| `doctor manages own assignments` | ALL | `doctor_email = yo` — **sin verificar el vínculo** |
| `pedu_doctor_lee` | SELECT | vínculo en `doctor_patients` |
| `pedu_doctor_asigna` | INSERT | vínculo en `doctor_patients` **y** firma propia |
| `pedu_doctor_quita` | DELETE | `doctor_email = yo` |
| `patient reads own assignments` | SELECT | `patient_email` = correo del token |
| `pedu_paciente_lee` | SELECT | `patient_email` ∈ `patients` del `auth.uid()` |
| `patient marks own as read` | UPDATE | `patient_email` = correo del token |
| `pedu_paciente_marca_leido` | UPDATE | ídem, con `with check` |

### Qué deja pasar la primera

`doctor manages own assignments` es `for all` con
`doctor_email = auth.jwt()->>'email'` en el `using` **y** en el `with check`.
Para SELECT, UPDATE y DELETE eso es correcto: solo toca filas propias. El
problema es el **INSERT**.

Como el `with check` solo mira `doctor_email`, un profesional puede insertar
una fila con **cualquier** `patient_email` del sistema mientras firme con el
suyo. No hace falta vínculo. `pedu_doctor_asigna`, que sí lo exige, queda sin
efecto: las dos se combinan con OR y basta que una permita.

Dos consecuencias:

1. Un profesional puede meter material en la pantalla de inicio de un
   paciente que no es suyo. El paciente ve "tu profesional te recomienda
   leer esto" de alguien que no es su profesional.
2. Peor: queda un **oráculo de enumeración**. Se inserta una fila con un
   correo cualquiera y después se lee esa misma fila (es propia, así que la
   policy la deja). Si `read_at` se completa, ese correo es de un paciente
   activo de Dormetria. Eso es dato de salud por inferencia — Ley 25.326
   art. 7 — obtenido sin ninguna relación asistencial.

No hay lectura de datos clínicos ajenos: para leer filas de otros, hace
falta el vínculo (`pedu_doctor_lee`) o ser el dueño de la fila.

### El arreglo

Una línea. Las tres `pedu_doctor_*` cubren lo que la app hace —leer, asignar
y quitar—, y las dos del paciente cubren su lado.

```sql
drop policy if exists "doctor manages own assignments"
  on public.patient_education;

notify pgrst, 'reload schema';
```

Después queda así, y tiene que dar **7 filas**:

```sql
select policyname, cmd,
       qual       as usando,
       with_check as al_escribir
from pg_policies
where schemaname='public' and tablename='patient_education'
order by cmd, policyname;
```

> **Lo que queda sin policy a propósito:** el profesional no tiene UPDATE.
> La app nunca lo hace —asigna con POST y desasigna con DELETE—, y un UPDATE
> sin vínculo sería el mismo agujero por otra puerta. Si alguna vez hace
> falta, se escribe con el `exists` contra `doctor_patients`, no con un
> `for all`.

> **Si algo deja de andar al borrarla**, el síntoma sería que el panel
> Material no asigna. Querría decir que la ficha del paciente se abre sin
> una fila en `doctor_patients`, que es un problema aparte y más grave. Se
> vuelve atrás corriendo de nuevo el bloque de policies de más arriba.
